Session 30: database-level account deletion security, design review

2026-11-22 · Claude Code (Opus 5.5) · Design review only · No code, schema, privilege or data change · Nothing committed or pushed

Question

Session 29 showed that a rider can only request their own deletion through the app, but that the database cannot tell a genuine request from one written by a compromised application role. What can the database itself guarantee, and at what cost?

Findings

#SeverityFinding
F1highThe production template puts the owner credentials (DB_MIGRATION_*) in the web runtime. Anyone who reads that environment bypasses every database protection: the append-only audit log, both guard triggers, and the redaction checks.
F2mediummrn_app can delete from 57 tables, including users. Only the deletion run needs to delete a rider row.
F3mediummrn_app can delete deletion records (only the purge needs that) and moderation evidence (never needed).
F4mediummrn_app can write the migrations table, which it never needs, so a future security migration could be skipped.
F5lowA fabricated request waits 30 days, but F2 means a misused app role doesn't need a request at all.

Already enforced in the database:

  • the audit log is insert-only for the app role;
  • system and redaction entries come only from the owner role;
  • request dates come from the database clock and cannot be moved;
  • an evidence hold can't exceed 30 days;
  • a rider row can't be deleted while it still authors non-anonymised content or organises a non-cancelled event.

Options

OptionSummaryVerdict
AKeep the current stateF1 to F5 remain
BOwner credentials out of the runtime; revoke DELETE on users, deletion records and evidence, and writes on migrations; definer functions mrn_delete_account(request) (checks a due request by the database clock) and mrn_purge_deletion_records()recommended; about half a session
CA separate database role for the daily jobsweaker against SQL injection and a compromised host; could be added on top of B later
DThe whole deletion run as one stored procedurenot proportionate: duplicated rules, hard to test

The implementation plan, test plan, clock and test design (timing checks skipped for owner-role sessions, proven on the real app-role connection and in E2E), rollback and risks are in docs/security/ACCOUNT_DELETION_DB_SECURITY_DESIGN.md.

Evidence gathered (read-only)

  • Grants: the app role's rights on the development database. It has full DML on 57 tables; the audit log is insert and select only.
  • Code search: the only rider-row delete is in ProcessAccountDeletion. Evidence is only created or updated, deletion records are deleted only by the purge, and migrations is never touched at runtime.
  • Existing checks: contributions_author_or_deleted and events_organizer_or_cancelled are present.
  • Credentials: .env.production.example lines 34–35, and config/database.php lines 103–110 (the pgsql_owner connection).
