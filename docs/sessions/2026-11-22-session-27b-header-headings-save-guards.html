What the tests cover

  • Header and headings (unit, homeHeader.spec.ts, 6 tests: the real header and home page, with the API mocked):
    • loading, API failure, rendered hero, and hero removed: header state and exactly one h1 in each;
    • leaving the home page restores the normal header;
    • a retry after an error keeps one h1 throughout.
    Proof: with the old header condition restored, 3 of the 6 tests fail (loading, failure, no hero).
  • Header and headings in real browsers (E2E, home-header.spec.ts, 4 tests × Chromium, Firefox, mobile): the home API is intercepted (held, a 500, or the hero removed), so no database rows change. Loading also checks the switch to transparent once the hero arrives. The hero case also checks that /explore keeps its normal header.
  • Staff double submits (unit, saveGuards.spec.ts, 8 tests: 4 forms × success and failure):
    • three submit events while the request is held give one service call;
    • the button reads "Saving…", is disabled and has aria-busy="true";
    • after success or failure, the label, enabled state and aria-busy="false" come back and a second request can go out.
    Proof: with the four guards removed, all 8 fail.
  • Staff service point in a real browser (E2E, save-guards.spec.ts, Chromium and Firefox): a real staff sign-in, the POST held, a double click on Add; "Saving…" is disabled and busy; exactly one POST and one database row; the button is restored.
