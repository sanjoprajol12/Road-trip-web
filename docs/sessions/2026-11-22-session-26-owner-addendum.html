O8: audit text redaction

  • Integrity: the audit log has no hash chain, signature or checksum, so redaction breaks no verification. A future chain must hash the redacted form and link each redaction record.
  • Still append-only: the app role still cannot update or delete audit rows. It may only call mrn_redact_audit_text(entry, reason), a security definer function owned by the table owner.
    • It accepts one reason (account_deletion) and three entry types: contribution edits, contribution corrections and place resubmissions.
    • It replaces only text fields with "[redacted]". Ids, times, actions, actors, subjects and IP addresses are kept, and no key is removed.
  • Every redaction is recorded: a separate audit.redacted entry, by system, names the affected entry, the fields and the reason, with no content and no person. A repeated call changes nothing and records nothing.
  • When it runs: only inside the account deletion run, for the departing rider's contributions and for the place suggestions deleted with the account. There is no HTTP route, and the migration cannot be rolled back once a redaction exists.

Found during verification: the append-only rule was off in two databases

  • In the development and E2E databases, the app role could update and delete audit rows. The test database was correct.
  • Cause: scripts/setup-local-db.sh grants update and delete on every table, which undid the append-only revoke whenever the script ran after the migrations.
  • Fixed: the script now re-applies the revoke, and the revoke is restored in both databases.
  • Checked as the app role in the E2E database: a direct update is refused, and the function redacts and records. The two check rows stay there, because the log cannot be edited.
  • Before production: confirm that has_table_privilege('mrn_app', 'audit_logs', 'update') is false.

D-10: deletion records kept one year

  • A finished or cancelled request keeps only:
    • the request and processing dates and the status;
    • choice categories (no contribution ids);
    • counts, including event and trip handovers, redactions and withdrawn corroborations;
    • the attempts and the error class.
  • The daily command deletes finished records one year after they finished, and audits the number deleted. Scheduled requests are never purged.
  • The pseudonymous account id stays for that year, so a deletion can be applied again after a backup restore.

D-11: corroboration recalculated

  • A report that the community threshold made "community corroborated" goes back to "published" when the remaining confirmers fall below the threshold. Each change is audited as contribution.corroboration_withdrawn, with the count and the threshold.
  • The remaining confirmers are counted without the time window and without re-checking other riders, so only the removal changes the outcome. The author is never counted.
  • A moderator's corroboration and an officially_sourced report are kept. The report stays published, and the API shows the new status.
