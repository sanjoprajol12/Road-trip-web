Stage 2: permissions foundation

  • Registry of 23 permissions in config/permissions.php; roles, permissions, permission_role; user_roles.role now references roles.slug (all existing assignments kept).
  • Built-in admin (every permission, always) and moderator (exactly the rights it had); custom roles; several roles per person.
  • No escalation: nobody creates, widens, narrows or gives a role beyond their own permissions; only administrators give admin; last active administrator protected.
  • Staff invitations (hash-only token, 72 h, single use), deactivation, admin-sent reset links, sign out everywhere; all audited.
  • Every staff route names a permission; the route test fails otherwise. Rider verification never grants a permission (tested).
  • Staff app: Roles page, People page with dynamic roles, invitations and account controls, invitation acceptance page, permission-driven menu and guard.

Stage 3: settings, media and storage (local disk)

  • Settings registry in code (general, maintenance, registration, storage): validated, cached, audited; secrets encrypted at rest, never returned, masked in the audit log (framework tested with a test-only secret; real secrets arrive with mail settings, Stage 9).
  • Public GET /api/v1/site; maintenance switch as a database flag (not artisan down, which is lost on Vercel): public API answers 503 with the message, staff and sign-in keep working, the public site shows "Back soon"; sign-up can be closed with a message.
  • Media library: licence limited to CC0, public domain or owner-supplied, credit required, used images cannot be deleted; every upload goes through one pipeline that honours the storage limits and re-encodes to WebP.
  • Every stored file records its disk and size, so old files keep working after a provider switch; storage test with usage figures. The S3-compatible driver waits for owner decision D1.

Security considerations

  • Permissions are checked by middleware and policies, never only in the UI; the route test covers every endpoint.
  • Invitation tokens are stored as SHA-256 hashes; an existing account cannot be taken over with a token alone.
  • Deactivated and suspended accounts lose sessions immediately and are refused at sign-in.
