Main findings

  • Strong and tested: accounts, sessions, roles, claim-specific verification, organizer-only hosting, event joining with capacity lock and waitlist, private group trips, the moderation gate, the append-only audit log.
  • Content model thinner than the specification: destinations have no attractions, permits, seasons, cost estimates or sources; routes have no difficulty, per-segment time, alternatives or filters.
  • Trust pipeline incomplete: no moderation transition rules (rejected can jump to officially sourced), no "request correction", no automatic outdating or corroboration, no last_confirmed_on on contributions, item history invisible to moderators.
  • Built API, no screen: "My events" (GET /users/me/events), editing a pending contribution (PATCH /contributions/{id}), email resend. Destination services and experiences are available from the API but not shown.
  • Consent gap: a trip owner can add any rider to a group trip without that rider accepting (journey J7 says members accept).
  • Scope regression: "saved services" (specification §6) was moved to "future recommendations" in session 4 without a recorded owner decision.
  • Safety areas have the review machinery but no content, as intended: content must come from qualified people.
  • Offline Ride Pack (agreed for a later milestone) is not started.

Architecture check

Implemented: web = Laravel API + public/rider SPA; admin = staff-only SPA. History: the session-1 addendum separated public and staff apps; the session-4 brief first placed all Vue code in admin; mid-session 4 the owner was asked directly and chose the current structure, recorded in five documents. That answer exists only in Claude-written documents, and today's brief calls the other structure "earlier approved". Flagged for owner confirmation. Nothing was restructured.
