2. Unauthorized deletion requests

Every path that creates or changes a request was traced:

  • The only one is ScheduleAccountDeletion::request($request->user(), …), behind POST users/me/deletion.
  • The route has no user parameter, and validation accepts only password, confirm and choices.
  • No staff route creates or alters requests. Choices for contributions that aren't the rider's own are refused (tested in session 25).

Owner role (migrations, tests, local fixtures)unrestricted by design: it owns the schema

Conclusion:

  • An ordinary application session cannot request another rider's deletion.
  • A compromised application database role can insert a request, but nothing in the database can tell it apart from a real one. The trigger delays its effect by 30 days.
  • The same role can already delete rows it has rights to, including users. Closing this needs an architectural change, which is an owner decision and was not made in this session: revoke DELETE on users from mrn_app, and remove accounts only through a definer function that checks a due request.
