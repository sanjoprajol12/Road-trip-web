Regression tests (AccountDeletionTest, 25 tests)

  • R8, the exact scenario: a moderator marks a report still accurate; two days later a rider confirms it; the rider deletes their account; the rider's confirmation is removed. The moderator's date is kept, the status stays published, and the API shows both. A repeated run changes nothing.
  • R8, other cases: a later moderator date is untouched, and a report with rider confirmations only is still recalculated.
  • R2, at the function:
    • a request still in its cooling-off is refused;
    • for a due request, the rider's own entries are accepted, including place.suggested;
    • repeated calls do nothing and write no second record;
    • refused: another (active) rider's entry; an unknown request or entry; an unsupported type; a mismatched subject type; an account in its cooling-off; a request shortened below 30 days; an account not marked for deletion.
  • R5: exceptions carrying an email, SQL and private text, raised in the run and in the evidence step, never appear in the captured logs. The request id and the exception class do. The request is retried and completes.
  • Switches: both default off. Both off: nothing changes. Purge only: deletions are not processed. Processing only: records are not purged.
  • R9: see the table above.
  • O8, D-10, D-11: the earlier tests still pass. The D-10 boundary probe was rerun through the new purge command: records exactly a year old and older are purged, a record one minute short is kept, scheduled requests are kept, and a second run purges nothing.

Security implications and remaining production requirements

  • Residual risk: a compromised app role can still create a deletion request for another rider. It can be used only 30 real days later, and the rider sees the deletion banner meanwhile. Anything the app role can do, a compromised app can do; this is the remaining limit.
  • Before production:
    • verify that mrn_app has no UPDATE or DELETE on audit_logs and is not a member of the owner role, and that both triggers exist;
    • set the cron;
    • connect a mail provider (O5);
    • get the owner's approval, then enable the switches, one at a time.
  • Deferred: the account-id HMAC, with a restore-replay design and key lifecycle.
