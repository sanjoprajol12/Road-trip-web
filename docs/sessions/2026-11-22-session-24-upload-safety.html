What was built

  • One policy (App\Support\UploadPolicy) is checked before every new file, in this order:
    1. UPLOADS_ENABLED (env) is on;
    2. the staff setting storage.uploads_enabled is on;
    3. the chosen disk is configured;
    4. the local disk is used only in local or testing. There is no override (O6).
    If any check fails, the upload is refused with a 422 and the staff-set message. There is no fallback disk.
  • One write path: Images::store() runs the policy, then the existing validation, re-encoding and EXIF stripping, then the write.
    • It serves rider photos and the staff media library.
    • A failed write leaves no database row.
    • A failed row deletes the file.
  • Critical log when storage is unusable, with only the reason, disk, driver and environment. It is written at most once an hour per reason. A deliberate pause writes no log.
  • Visible state:
    • /site and /health report whether uploads are paused.
    • The public site and the staff media library show the message in place of the picker. The report form still sends.
    • Staff Settings → Storage shows why uploads are paused, with a toggle and an editable message.
    • Existing images are served in every state.
  • Isolation: browser tests store files under storage/app/e2e (LOCAL_DISK_ROOT), apart from development files.

Safe production configuration

APP_ENV=production
UPLOADS_ENABLED=false
FILESYSTEM_DISK=local

This is also in .env.production.example. If UPLOADS_ENABLED is left true by mistake, production still refuses the local disk, and each refusal is logged as critical.

Next

To add a provider:

  1. get the package approved;
  2. configure the disk;
  3. allow its value in storage.driver;
  4. choose it in Settings and run "Test storage";
  5. set UPLOADS_ENABLED=true and verify uploads.

Only then may persistent storage be called operational. Otherwise, continue with the decision-record order, starting with account deletion.
